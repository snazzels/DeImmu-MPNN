## A note on the numbers in this tree

Percentage reductions are per-protein means, and a protein whose base
designs present almost no epitopes has an unusable denominator. Files
named `*_guarded_summary.txt` exclude proteins with a mean base burden
<= 1.0 window; the plain `*_summary.txt` beside them do not, and are
superseded for every reported value. Where both exist, **the guarded one
is the paper's number.**

## `data/monomer_eval/`

Sec 3.1 headline: 100 held-out proteins, deployed model. netMHCIIpan **41.4%** (the guarded value -- see below), MixMHC2pred 33.3%, netMHCpan MHC-I 33.0%, and the Fig 3A external MHC-I-only arm.

**Read the `*_guarded_summary.txt` files, not the older `*_summary.txt` beside them.** The originals computed each per-protein percentage reduction with no minimum-base guard, so a protein presenting 0.10 windows on average contributed -300% and depressed the headline from 41.4% to 37.9% (2026-08-25). Both are shipped: the guarded summary is the reported number, the original is kept so the correction is auditable. `analysis/recompute_guarded_reduction.py` regenerates the former from the unchanged CSVs.

The %Rank cutoff series (1/2/5/10%) is shipped TWICE and only one of the two is the paper's. **Use `validate_netmhciipan_rank_sensitivity_deployed_sweep_guarded_summary.txt`: 44.0 / 41.4 / 37.7 / 35.1%, improved 93/98, 93/98, 94/99, 97/100.** Its 2% entry reproduces the 41.4% headline, which is the property the manuscript's argument rests on, and it carries a per-protein CSV so any future change to the exclusion rule is an offline recompute rather than another 4 h netMHCIIpan pass. `validate_netmhciipan_rank_sensitivity_f16b51e6_summary.txt` is the SUPERSEDED predecessor (43.5 / 37.9 / 37.8 / 35.1%): unguarded, and drawn from a different base arm, so its 2% value does not reproduce the headline. It is retained only so the correction is auditable. Re-run: `training/slurm/21_rank_sensitivity_guarded.sbatch` (job 519997, 2026-08-26).

**The three lambda arms of Table tab:sweep cannot be told apart from their netMHCIIpan summaries, and this is a trap.** All three `validate_netmhciipan_fullset_lambda{0,05,10}_k10_summary.txt` carry the same hardcoded banner `CAPE-MPNN 057975d5 vs BASE` -- a stale script string, not the model that was run (and `057975d5` is itself the hash-collision id: lambda=0 in v1, overwritten by lambda=0.5 in v2). ## `data/binder_panel/`

Sec 3.5 / Table tab:panel: 11 de novo binder complexes. netMHCIIpan 50.4%, MixMHC2pred 40.4%, netMHCpan MHC-I 30.2%, Boltz-2 ipTM 0.866->0.857, AF2 initial-guess 40.5->44.3%.

**Where each tab:panel column comes from, since none of it is guessable from the filenames.** Binder length, Boltz-2 ipTM (base/cape) and the AF2-ig pass percentages are COLUMNS INSIDE `panel11_v2_f16b51e6_results.csv` (`iptm_base`/`iptm_cape`, `af2ig_base_pass_pct`/`af2ig_cape_pass_pct`) -- there is no separate af2ig data file, so searching by filename finds nothing. The MHC-II and MHC-I reduction columns come from the `validate_net*_binderpanel_v2` files. `burden_results_v2.json` carries the per-complex interface/core/surface **mutation rates** behind Sec 3.7 (interface base 0.555 -> cape 0.566, paired p=0.41; surface 0.617 -> 0.614), under `base|cape -> mut_rate -> I|C|S`; the paired statistic itself was never written to a summary and is recomputed from this JSON.

`validate_binder_negative_control.*` is the **disruption control**: the four strongest-interface complexes with their binder interface residues permuted (composition preserved) and re-folded identically. Native ipTM 0.933 -> scrambled 0.503, a 0.430 drop, roughly a hundredfold larger than the base-vs-fine-tuned difference -- which is what makes that difference a genuine null rather than an insensitive validator. **⚠️ Its driver script is not deposited because none survives: this control was run ad hoc and no `.py` in the project writes these files.** The component machinery IS here (`application/contacts.py` for the interface definition, `application/boltz_gen_yaml.py` and `boltz_parse.py` for the fold and parse), so the control is re-implementable, but it is not re-runnable from a single deposited script. The per-complex CSV is shipped so the numbers stand on their own regardless.

## `data/attribution/`

Fig 3A and Supplementary Table tab:supp-stats, objective attribution (the double dissociation). Class II-only `abec4d2c` vs deployed `f16b51e6`, scored on ONE matched protein set against a base arm that is identical design by design, by two predictors neither objective was trained against (netMHCIIpan, netMHCpan) plus MixMHC2pred.

**Why matched files rather than each model's own run.** Two arms scored on separately drawn base designs differ for two reasons at once -- the model and the draw -- and the two cannot be separated afterwards. Where a guarded summary exists it is the reported value and the plain `_summary.txt` beside it is superseded; where none exists the guard was inactive for that file and the plain summary stands.

## `data/sweep/`

SI Fig A (Pareto front) and Table tab:sweep: all 15 beta x learning-rate configurations, netMHCIIpan + MixMHC2pred + sequence recovery + MHC-I arm.

**Two families live here and only one is Table tab:sweep's lower-rate row.** `validate_netmhciipan_sweep_<id>.csv` (13 model ids) is the beta x lr grid, one independently drawn sample per configuration. `validate_netmhciipan_sweep_ep200_pinned98_lambda{0,05,10}` is the **matched** lambda series added 2026-09-14: one pinned 98-protein sample and one shared base arm across all three arms, which is what makes the rows of `tab:sweep` comparable protein-to-protein.

**Use the `_guarded_summary.txt` of the `ep200_pinned98_lambda*` trio for the lambda series: 31.95 / 29.49 / 28.75%**, which is the manuscript's 31.9 -> 29.5 -> 28.8% at the lower learning rate. Those summaries apply the minimum-base guard AND exclude the four assembly-mismatched proteins (`2pt5_B`, `3hmt_A`, `4i4y_C`, `4nc7_B`) plus `4b6d_C`, leaving n=93. The plain `_summary.txt` beside each is the unguarded n=94 value and does not reproduce the paper.

**Do not read a lambda trend off the 13 grid files.** They were drawn on 13 different protein samples, so a difference between any two of them confounds the model with the draw. That confound is exactly what the matched trio was run to remove -- before it existed the lambda trend looked flat, and matched it is monotone at a cost of roughly 3.2 points across the series. Run `analysis/check_protein_match.py` before quoting any cross-file difference here.

## `data/robustness/`

Robustness probes on the Sec 3.1 headline, one file pair each. All are re-scorings of the frozen `validate_netmhciipan_sweep_f16b51e6.csv`, so the protein sample and base arm are identical to the headline's by construction.

- **`unique_core_sweep_*`** -- is the 41.4% inflated by counting overlapping 15-mer windows? Recounting distinct (allele, binding-core) pairs gives **39.54%** against the window metric's **41.36%**, a gap of 1.8 pp, with windows per unique core falling 2.70 -> 2.61. The two metrics agree, so the overlap-counting objection does not bite. Carries an acceptance test: every per-design window count reproduces the published `netmhc_total` exactly.
- **`filtering_ensemble_sweep_*`** -- does post-hoc filtering of a base ensemble reach fine-tuning given a large enough budget? Not within the range the ensembles support: best-of-k reaches **36.36%** at k=10 against the fine-tuned **41.36%**, a 5.0 pp shortfall, and the published keep-3-of-10 rule reaches 26.27%. The estimator is the exact expectation of the best of k drawn from 10, not a bootstrap. The curve is monotone, so a crossing at some larger k is not excluded; what is excluded is a crossing within the tested range.
  **Use the `_v2` pair.** v1 tabulates best-of-k only; v2 adds the keep-3-of-k rule, which is the one behind the manuscript's filtering baseline, plus an acceptance test against the published 26.60% (recomputed 27.02%, +0.42 pp, unguarded on all 99). v1 is kept as the provenance of the earlier figure and is superseded for every reported value.
- **`developability_panel_*`** -- did the objective move any liability axis? Ten sequence-level proxies, paired per protein, Holm-Bonferroni across all ten. Six moved toward higher liability, four toward lower. The large one is **cysteine, 2.36 -> 11.39 per protein (+9.03, a factor of 4.8, p=4e-28 raw)**; also tryptophan (+2.15), methionine (+0.85), N-glycosylation sequons (+0.39) and deamidation motifs (+0.53, +0.35), against reductions in hydrophobic patches (-3.72) and DG/DS isomerisation (-0.26). CamSol, Aggrescan3D and SAP were NOT run: these are proxies for CHANGE between two arms designed from identical backbones, and no absolute aggregation risk is claimed.
- **`human_kmer_match_*`** -- are the designs becoming less human-self-like, which would raise immunogenicity by a route the burden metric cannot see? No: the 9-mer match rate against 20,431 SwissProt human proteins moves 0.869% -> 0.745%, a paired difference of **-0.124 pp, 95% CI [-0.288, +0.040], p=0.137** -- if anything less self-like, and not significant. A bounded negative result, not equivalence. Use the `_v2` pair: its numbers are identical to v1's and it additionally documents that the 7,500 skipped windows (1.414%) are those spanning a chain separator or an unknown residue. Note the deliberate convention difference recorded in that file: this tool EXCLUDES 9-mers crossing a chain junction, while the 15-mer window builders behind the burden metric STRIP the separator and therefore do count across junctions. That is preserved because the published counts depend on it.
- **`strong_binder_survival_*`** -- is the reduction carried by marginal binders, leaving the immunodominant end untouched? No: at netMHCIIpan's strong-binder threshold (%Rank_EL <= 1) the reduction is **43.97%**, slightly above the 41.39% at the reported <= 2 cutoff, falling monotonically to 35.14% at <= 10. No protein is left with zero predicted strong binders in either arm, so the reduction is a shift in degree, not elimination.

- **`rosetta_mhc_epitope_*`** (P2-1) -- does the reduction survive a predictor unrelated to netMHCIIpan? The training reward is a PWM fitted to netMHCIIpan and every reported number comes from netMHCIIpan, so this scores the same designs with Rosetta's `mhc_epitope` term over the ProPred/TEPITOPE matrices for eight HLA-DR alleles -- a PSSM over 9-mers, predating netMHCIIpan, fitted to different data. **The reduction replicates in direction and significance but not in magnitude: 11.93% of ProPred windows (16.94% of allele-summed hits) against netMHCIIpan's 41.36% on the same 98 proteins, 90/98 improved, p=5e-16.** The instrument is valid on these proteins -- base-arm Spearman against netMHCIIpan is +0.80 (p=2e-223), so the two agree about which designs are epitope-rich and the magnitude gap is a finding rather than noise. Also reports IEDB 9-mer membership (Rosetta's shipped 190,594-peptide set), which is flat and uninformative here -- 94 of 98 proteins have zero base hits, so it excludes nothing.

## `analysis/`

Every script that produces the data above.

`recompute_guarded_reduction.py` is the one to read first if a number here disagrees with an older summary: it applies the minimum-base guard to a frozen validator CSV and writes a `*_guarded_summary.txt` without re-scoring anything. `check_protein_match.py` should be run before comparing any two runs -- it verifies the protein sets match, though not that the base designs do.

The five probes added 2026-09-09 (`unique_core_sensitivity.py`, `filtering_ensemble_sweep.py`, `developability_panel.py`, `human_kmer_match.py`, `strong_binder_survival.py`) all take a frozen validator CSV as input rather than re-scoring designs, so they reproduce `data/robustness` from the deposited data alone, with no netMHCIIpan installation and no GPU. Each refuses to overwrite an existing output and versions its filenames instead, which is why two of them have `_v2` pairs.

The five added 2026-09-30 close the gap between this tree (frozen at manuscript v55) and v124. `human_proteome_reference.py` draws and scores the 400-protein human reference set the availability statement promises; `plot_human_reference.py` plots it and recomputes nothing but the between-population tests, so the figure cannot drift from the summary. `dp_orientation.py` is the forward-only HLA-DP re-score behind Supplementary Methods `supp:alleles`. `selfconsistency_binder_chains_boltz.py` folds the two binder chains ESMFold2 could not reach (9cce at 197 aa, 9nds at 248 aa), and `build_register_pwm_production.py` builds the register-anchored 9-mer PWM named in Methods.

**`selfconsistency_binder_chains.py` (no `_v2`) is deliberately NOT deposited.** It differs from the shipped `_v2` in two path constants alone, pointing at the superseded `binder_redesign_v1` design set instead of the deployed model's `binder_redesign_v2_f16b51e6`. Depositing it would ship a script that silently reads a design set absent from this tree and reproduces no published number.
